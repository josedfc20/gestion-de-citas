# Paso 3.2 · Arquitectura del backend

> Propuesta pendiente de revisión. Diagrama: `diagramas/Arquitectura-Backend.png`.

## 1. Estilo: monolito modular en capas

- **Un solo backend** (un único proyecto Spring Boot y un único despliegue).
  Para un negocio y un equipo pequeño, los microservicios añadirían complejidad
  sin aportar nada.
- **Organizado por funcionalidad** (*package by feature*): cada carpeta es un
  módulo del negocio (citas, servicios, horarios…), y dentro de cada uno se
  repiten las mismas capas. Así, todo lo relacionado con las citas está junto y
  es fácil de encontrar y ampliar (RNF-006).

## 2. Las capas y su responsabilidad

| Capa | Qué hace | Qué NO hace |
|---|---|---|
| **Controller** | Recibe la petición HTTP, valida el formato del DTO (`@Valid`), llama al servicio y devuelve JSON con el código HTTP adecuado. | No contiene reglas de negocio ni accede a la base de datos. |
| **Service** | Aplica las reglas de negocio (RN-001…RN-011), comprueba permisos, coordina repositorios y abre la **transacción** (`@Transactional`). | No sabe nada de HTTP ni de JSON. |
| **Repository** | Lee y guarda entidades con Spring Data JPA (consultas). | No decide nada de negocio. |
| **Entidad** | Representa una tabla (diagrama de clases → JPA). | No se envía nunca directamente al cliente. |
| **DTO** | Objetos de entrada/salida de la API (por ejemplo `ReservaRequest`, `CitaResponse`). | No se guarda en la base de datos. |

Regla de dependencias: **Controller → Service → Repository**, nunca al revés,
y un controller nunca llama directamente a un repository.

```
com.gestiondecitas
├── GestionDeCitasApplication.java
├── auth/            → registro, login, recuperar contraseña (CU-001, 002, 003, 020)
├── usuario/         → Usuario, Cliente, Empleado, perfil (CU-004)
├── beneficiario/    → menores a cargo (CU-009)
├── servicio/        → catálogo (CU-005, CU-016)
├── empleado/        → gestión de empleados y servicios asignados (CU-006, 017, 021)
├── horario/         → tramos y días de cierre (CU-018)
├── disponibilidad/  → cálculo de huecos libres (CU-007)
├── cita/            → reservar, cancelar, estados, historial (CU-008…015, 019)
├── negocio/         → configuración del negocio (Negocio)
└── shared/
    ├── config/      → configuración de Spring, Clock, OpenAPI
    ├── security/    → Spring Security, JWT, roles
    └── error/       → excepciones y manejador global de errores
```

Dentro de cada módulo, por ejemplo `cita/`:

```
cita/
├── CitaController.java
├── CitaService.java
├── CitaRepository.java
├── Cita.java                 (entidad)

├── dto/  ReservaRequest.java, CitaResponse.java, CambioEstadoRequest.java
└── CitaMapper.java           (entidad ↔ DTO)
```

## 4. Decisiones transversales

### 4.1 Nunca exponer entidades: siempre DTOs
Si devolviéramos la entidad `Usuario`, saldría `passwordHash` en el JSON. Los
DTOs dejan elegir exactamente qué entra y qué sale, y permiten cambiar la base
de datos sin romper la web ni la app Android.

### 4.2 Validación en dos niveles
- **Formato** en el DTO con anotaciones: `@NotBlank`, `@Email`, `@Future`…
- **Reglas de negocio** en el servicio: 24 h para cancelar, 60 días de
  antelación, edad mínima, duración múltiplo del intervalo.

### 4.3 Errores uniformes
Un `@RestControllerAdvice` convierte las excepciones en respuestas con el
formato estándar **Problem Details (RFC 9457)**, que Spring Boot 3 soporta de
serie. Ejemplos:

| Situación | Excepción | HTTP |
|---|---|---|
| Datos con formato incorrecto | `MethodArgumentNotValidException` | 400 |
| Sin sesión | — (Spring Security) | 401 |
| Sin permiso (otro cliente, otro empleado) | `AccessDeniedException` | 403 |
| No existe la cita | `RecursoNoEncontradoException` | 404 |
| Hueco ya ocupado (solape rechazado por PostgreSQL) | `HuecoNoDisponibleException` | 409 |
| Fuera de plazo de cancelación | `ReglaNegocioException` | 422 |

### 4.4 El reloj inyectable (`Clock`)
Las reglas dependen de "ahora" (24 h, 60 días, edad). En lugar de llamar a
`LocalDateTime.now()` por todo el código, se inyecta un `Clock`. En las pruebas
se usa un reloj fijo y así se puede probar "faltan 23 horas" sin esperar.

### 4.5 El cálculo de disponibilidad, aislado
`DisponibilidadService` recibe horarios, cierres, citas y configuración y
devuelve las horas libres, siguiendo el diagrama de actividad. Al no depender
de HTTP ni de la base de datos, se prueba con muchos casos con pruebas
unitarias rápidas.

### 4.6 Transacciones
Cada operación que escribe (reservar, cancelar, cambiar estado) es un método
`@Transactional` del servicio: guarda la cita **y** su `CambioEstadoCita` juntos
o no guarda nada (diagramas de secuencia).

### 4.7 Configuración
- Valores del negocio (30 min, 60 días…) en la tabla `negocio`.
- Valores técnicos (URL de la base de datos, claves) en `application.yml` y
  variables de entorno, **nunca** en el código ni en Git.

## 5. Cómo encaja con lo diseñado

| Diseño (fase 2) | Dónde vive (fase 3) |
|---|---|
| Diagrama de clases | Entidades JPA de cada módulo |
| Esquema SQL | Migraciones Flyway (`db/migration/V1__esquema_inicial.sql`) |
| Casos de uso | Métodos de los servicios (uno o varios por CU) |
| Secuencias | Flujo Controller → Service → Repository |
| Actividad "Calcular disponibilidad" | `DisponibilidadService` |
| Diagrama de estados | Método que valida transiciones en `CitaService` |
