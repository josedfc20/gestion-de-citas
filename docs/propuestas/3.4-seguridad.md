# Paso 3.4 · Seguridad y autenticación

> Propuesta pendiente de revisión.

## 1. Cómo se inicia sesión: JWT + token de refresco

Como la misma API la usarán la web y la app Android, propongo **tokens** en vez
de sesiones guardadas en el servidor.

| Token | Qué es | Duración | Dónde se guarda |
|---|---|---|---|
| **Access token** (JWT) | "Pase" firmado que dice quién eres y tu rol. Se envía en cada petición: `Authorization: Bearer ...` | **15 minutos** | Web: solo en memoria (nunca en `localStorage`). Android: en memoria. |
| **Refresh token** | Código aleatorio para pedir un access token nuevo sin volver a escribir la contraseña | **7 días** | Web: cookie `HttpOnly`, `Secure`, `SameSite=Strict`. Android: almacenamiento cifrado. |

### Flujo
```
1. POST /auth/login (email + contraseña)
   → 200 { accessToken }  + cookie refresh_token
2. Peticiones normales con   Authorization: Bearer <accessToken>
3. Al caducar (401) → POST /auth/refresh con la cookie
   → nuevo accessToken y NUEVO refresh token (el anterior queda invalidado: rotación)
4. POST /auth/logout → se revoca el refresh token
```

**¿Por qué así?**
- El access token dura poco: si alguien lo roba, sirve muy poco tiempo.
- El refresh token va en una cookie `HttpOnly`, que JavaScript no puede leer, así
  que un script malicioso (XSS) no puede robarlo.
- Con la **rotación**, si alguien reutiliza un refresh token ya usado, se
  detecta el robo y se revocan todos los tokens de ese usuario.
- El logout es real: el refresh token se revoca en la base de datos.

**Cambio en la base de datos (paso 2.6):** hace falta una tabla nueva:
```sql
CREATE TABLE refresh_token (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    usuario_id  BIGINT NOT NULL REFERENCES usuario(id),
    token_hash  VARCHAR(100) NOT NULL UNIQUE,   -- con hash, como las contraseñas
    expira_en   TIMESTAMPTZ NOT NULL,
    revocado    BOOLEAN NOT NULL DEFAULT FALSE,
    creado_en   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 2. Contraseñas (RNF-001)
- Hash con **BCrypt** (factor de coste 12), el estándar de Spring Security.
- Política mínima: **10 caracteres**, sin reglas raras de símbolos (recomendación
  actual del NIST), y se rechazan contraseñas muy comunes ("1234567890").
- Mensajes genéricos en el login: "correo o contraseña no válidos".

## 3. Autorización: roles y propiedad (RNF-002)
Dos niveles:
1. **Por rol**, en Spring Security, según la ruta:
   - `/api/v1/admin/**` → solo `ADMIN`
   - `/api/v1/empleado/**` → solo `EMPLEADO`
   - `/api/v1/me/**`, `POST /citas` → usuario con sesión
   - `/servicios`, `/profesionales`, `/disponibilidad`, `/auth/**` → públicos
2. **Por propiedad**, en el servicio: aunque tengas el rol, solo ves y cambias
   **lo tuyo** (tus citas como cliente, tu agenda como empleado). Si no es tuyo
   → 404 (paso 3.3).

## 4. Protección contra abusos
| Riesgo | Medida |
|---|---|
| Probar contraseñas a lo bruto | Límite de **5 intentos de login por minuto** por IP y por email (Bucket4j) |
| Abusar de "recuperar contraseña" | Límite de **3 solicitudes por hora** por email |
| Otra web llamando a nuestra API | **CORS** solo permite el dominio de nuestra web |
| Ataques CSRF con la cookie de refresco | `SameSite=Strict` y cookie limitada a la ruta `/api/v1/auth/refresh` |
| Inyección SQL | JPA con parámetros; nunca concatenar SQL |
| Datos sensibles en los logs | Nunca registrar contraseñas, tokens ni datos personales completos |

## 5. Comunicación y secretos
- **HTTPS** obligatorio en el despliegue (RNF-004).
- La clave de firma del JWT, la contraseña de la base de datos, etc. van en
  **variables de entorno**, nunca en el código ni en GitHub. En el repositorio
  habrá un `.env.example` sin valores reales.

## 6. RGPD (RNF-007)
- Consentimiento guardado con fecha (`cliente.privacidad_aceptada_en`).
- Exportar mis datos: `GET /me/datos` devuelve en JSON los datos personales del
  usuario (derecho de acceso). **Es un endpoint nuevo** respecto al paso 3.3.
- Eliminar cuenta: anonimización (paso 2.6).
