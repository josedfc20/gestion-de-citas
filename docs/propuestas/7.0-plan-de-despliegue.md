# Paso 7.0 · Plan de la fase 7 (Despliegue)

> Aprobada el 14/11/2026, **sin ningún coste (0 €)**: servidor gratuito
> *Always Free* de Oracle Cloud (plan B: Render con la base de datos en Neon),
> Caddy, subdominio gratuito de DuckDNS, Brevo con su plan gratuito y el
> perfil `demo` restablecido cada noche. Fase 7 (Despliegue).
> La fase 6 está cerrada: el cierre se fusionó en `main` con el PR #26.

Según la tabla de fases, la fase 7 tiene que **preparar una versión que pueda
utilizarse y demostrarse**. Hasta ahora la aplicación solo funciona en tu PC:
la web la sirve Vite, el correo se queda en Mailpit y no hay HTTPS. La fase
consiste en **empaquetarla para producción, protegerla, publicarla en una
dirección pública con HTTPS y dejar escrito cómo se despliega y se mantiene**,
para que cualquiera (un reclutador, el tribunal) pueda abrirla desde el móvil.

## 1. Punto de partida (revisado hoy en `main`)

Lo que las fases anteriores dejaron apuntado para la fase 7:

| Tema | Estado | De dónde sale |
|---|---|---|

| Cabeceras de la web (CSP, HSTS) | Solo se comprueban las del backend (`seguridad.spec.ts`); las de la web dependen del servidor | 5d |
| Análisis de dependencias | Ninguno: no hay Dependabot ni `npm audit` en la CI | 5d |
| Proveedor SMTP real | `EnvioCorreoSmtp` ya habla SMTP; solo falta la configuración | B3 |
| Web y API en la misma dirección | En desarrollo lo hace el proxy de Vite; en producción falta quien lo haga | B7 |
| Entorno `prod` | "Se decidirá en la fase 7" | 3.5 |
| Login desde el móvil | No funciona en local porque la cookie es `Secure`; con HTTPS funcionará | Guía `arrancar-web.md` |

Y dos cosas que he encontrado al revisar el código para este plan:

- **Defecto latente (será el D-9):** el límite de intentos de login y de
  recuperar contraseña cuenta por IP con `peticion.getRemoteAddr()`
  (`AuthController`). Detrás de un proxy, todas las peticiones llegan desde la
  IP del proxy, así que **todos los usuarios compartirían los 5 intentos por
  minuto**. Se arregla en el 7a haciendo que Spring lea la IP real de
  `X-Forwarded-For`, pero solo cuando viene del proxy propio, con su prueba.
- **Swagger es público** (`/swagger-ui.html`, `/v3/api-docs`). En producción
  propongo apagarlo: la especificación ya está en `docs/api/openapi.json`.

## 2. Cómo quedaría desplegada

```
Navegador ──HTTPS──▶ Caddy ──┬── /          → la web compilada (archivos estáticos)
                             └── /api/...   → backend (Spring Boot, red interna)
                                                 ├── PostgreSQL 16 (red interna, sin puerto abierto)
                                                 └── SMTP del proveedor de correo
```

Todo en **Docker Compose** en un servidor pequeño. **Caddy** consigue y
renueva solo el certificado de Let's Encrypt, sirve la web, reenvía `/api` al
backend (web y API en la misma dirección, como el proxy de Vite, así que la
cookie del refresh viaja sin CORS) y pone las cabeceras de seguridad. Solo los
puertos 80 y 443 dan a Internet.

## 4. Decisiones

**Resultado (14/11/2026):** Jose prefiere no pagar nada mientras la
aplicación no genere ingresos, así que todo se hace con planes gratuitos:

| N.º | Decisión tomada |
|---|---|
| 1 | **Oracle Cloud *Always Free*** (servidor real con Docker Compose). Pide una tarjeta solo para verificar; la cuenta nunca se pasa a "pago por uso". Si no hay máquina libre o Oracle la recupera por estar sin uso, **plan B: Render + Neon** (gratis, pero la web se duerme). Las condiciones se comprueban justo antes del alta |
| 2 | **Caddy** |
| 3 | **Subdominio gratuito de DuckDNS**; un dominio propio se puede poner después cambiando una línea |
| 4 | **Brevo, plan gratuito**, con remitente verificado |
| 5 | **Perfil `demo`** con las cuentas de cliente y empleado en el README, la de admin solo para Jose y la base restablecida cada noche |

Las opciones que se plantearon:

1. **Dónde se despliega.** Propongo **un servidor virtual (VPS) pequeño**
   en Europa con Docker Compose (2 GB de RAM bastan; en proveedores como
   Hetzner o OVH cuesta unos 4 a 6 € al mes). Es lo que más enseña, no se
   duerme, no caduca, los datos se quedan en la UE (RGPD) y el mismo
   `docker-compose.prod.yml` sirve en cualquier otro servidor. Alternativas:
   (a) una **plataforma gestionada** (Render, Railway, Fly.io): menos trabajo
   de servidor, pero los planes gratuitos se duermen o borran la base de
   datos al cabo de un tiempo, y los de pago cuestan algo más; (b) **solo en
   tu PC** con el mismo Compose y un certificado local: gratis, pero sin
   dirección pública que enseñar.
2. **Quién sirve la web y pone el HTTPS.** Propongo **Caddy**: HTTPS
   automático y renovado solo, y una configuración de unas 30 líneas. La
   alternativa clásica es **Nginx + Certbot**: muy extendida, pero hay que
   montar y vigilar la renovación del certificado. Otra es que **Spring Boot
   sirva también la web** (un solo contenedor), pero mezcla las dos partes y
   el HTTPS seguiría necesitando un proxy delante.
3. **Dominio.** Propongo **un dominio propio** (unos 10 € al año, por
   ejemplo `gestiondecitas.es` o el que prefieras): queda mejor en el
   portfolio y es necesario para enviar correo con tu propio remitente sin
   caer en spam. La alternativa es un **subdominio gratuito** (DuckDNS):
   el HTTPS funciona igual, pero el correo tendría que salir con un remitente
   prestado y llegaría peor.
4. **Proveedor de correo.** Propongo **Brevo** por SMTP: empresa europea,
   plan gratuito con unos 300 correos al día (de sobra: solo se envía el de
   recuperar contraseña; lo confirmo al darte de alta) y sin cambiar el
   código. Alternativas: **Resend** (también gratuito, muy sencillo, empresa
   de EE. UU.) o **Gmail con contraseña de aplicación**: inmediato, pero con
   remitente `@gmail.com` y no está pensado para correos de una aplicación.
5. **Qué datos tiene la versión pública.** Propongo **el perfil `demo`**,
   con las cuentas de cliente y de empleado publicadas en el README para que
   cualquiera la pruebe, la de administrador solo para ti (se la das a quien
   quieras), y **la base de datos se restablece cada noche** con una tarea
   programada en el servidor, para que lo que toquen los visitantes no se
   acumule. La alternativa es arrancar sin demo (solo el admin) y enseñarla
   tú en cada presentación: más control, pero nadie puede probarla solo.

## 5. Lo que no entra en la fase 7

- **Alta disponibilidad, varios servidores o Kubernetes:** para una demo
  basta un servidor; el Compose se puede llevar a otro sin cambios.
- **Monitorización avanzada** (Prometheus, Grafana): solo el `health` que ya
  existe, los logs de Docker y, si quieres, un aviso gratuito de caída
  (UptimeRobot) que apuntaría la guía.
- **Firefox y Safari en las E2E:** siguen solo en Chromium; la ronda manual
  del 7f incluye abrirla en el navegador de tu móvil.
- **La aplicación Android:** es la "aplicación posterior" de la tabla de
  tecnologías, después de cerrar el proyecto.
