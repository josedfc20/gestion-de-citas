# Paso 7c · Análisis de dependencias (mini propuesta)

> Aprobada el 14/11/2026, con las opciones recomendadas: excepción de 30 días
> para el aviso de Caddy, la CI falla con avisos altos o críticos con arreglo
> y CodeQL activado. Fase 7 (Despliegue).
> El 7b se fusionó con el PR #28.

La aplicación usa cientos de librerías que no hemos escrito: Spring y sus
dependencias en el backend, React y Vite en la web, Playwright en las
pruebas, y además lo que trae cada imagen de Docker (Ubuntu con el JRE,
Alpine con Caddy). De vez en cuando se descubre un fallo de seguridad en una
de ellas (un CVE). El 7c sirve para **enterarnos solos** cuando pasa y para
que **la CI no deje publicar una versión con un fallo grave que ya tiene
arreglo**.

## 1. Cómo está hoy (revisado en `main`)

| Qué | Herramienta | Resultado |
|---|---|---|
| Librerías de la web (`frontend/`) | `npm audit` | 0 avisos |
| Librerías de las pruebas (`e2e/`) | `npm audit` | 0 avisos |
| Imagen del backend (Ubuntu, JRE 21 y todas las librerías Java del `.jar`) | Trivy | 0 avisos altos o críticos |
| Imagen de la web (Alpine y el programa Caddy) | Trivy | **2 avisos altos dentro de Caddy** (ver §3) |

Trivy es un analizador gratuito de Aqua Security: mira el sistema de la
imagen y también las librerías que lleva dentro (los `.jar` de Java, los
binarios de Go como Caddy). Por eso basta con analizar las dos imágenes
para cubrir el backend entero; la web compilada no lleva sus librerías en la
imagen (van dentro de los `.js`), así que esas las revisa `npm audit`.

## 2. Qué lleva

| Parte | Contenido |
|---|---|
| **`.github/dependabot.yml`** (nuevo) | Dependabot revisa **cada lunes** si hay versiones nuevas y abre un PR por cada grupo: Maven (`backend/`), npm (`frontend/` y `e2e/`), GitHub Actions, las imágenes base de los dos `Dockerfile` y las de los Compose. Las versiones menores y de parche van **juntas en un solo PR por carpeta**; las mayores (por ejemplo, React 20), cada una aparte, porque pueden romper cosas. Como mucho 5 PR abiertos a la vez. Cada PR pasa la CI completa, así que solo hay que fusionar los que salen en verde |
| **CI: `npm audit`** | En el trabajo de la web: `npm audit --audit-level=high` (falla con avisos altos o críticos) |
| **CI: Trivy** | En el trabajo "Producción", sobre las dos imágenes que ya construye: falla con avisos **altos o críticos que tienen arreglo**; los demás salen en el resumen de la ejecución. La versión de Trivy, fijada |
| **`.trivyignore.yaml`** (nuevo) | Las excepciones, cada una con su motivo y **fecha de caducidad**: al caducar, la CI vuelve a fallar y obliga a revisarla |
| **`seguridad.yml`** (nuevo) | Un análisis **cada lunes** aunque nadie toque el código, porque los CVE aparecen sin que cambie nada nuestro. Si encuentra algo, GitHub te avisa por correo |
| **Documentación** | `docs/guias/dependencias.md`: qué hacer con un PR de Dependabot y con un aviso de Trivy o de `npm audit`; `AGENTS.md` y `Doc.docx` |

**Lo que haces tú (te digo dónde):** en GitHub, *Settings → Code security*,
activar las **alertas de Dependabot**, el **escaneo de secretos** y la
**protección al subir** (si alguien sube una contraseña o un token por
error, GitHub lo bloquea). Son gratis en repositorios públicos.

## 3. Los dos avisos de Caddy

Trivy encuentra dos fallos altos en librerías de Go que lleva dentro el
programa Caddy 2.11.9, que hoy es su **última versión**:

| Aviso | Qué es | ¿Tiene arreglo? |
|---|---|---|
| CVE-2026-78661 (`golang.org/x/net`) | Un HTML preparado puede hacer que el analizador de HTML gaste mucha memoria (denegación de servicio) | Sí en la librería (0.62.0), pero **todavía no hay un Caddy que la use** |
| CVE-2026-116587 (`go-jose`) | Unas claves RSA preparadas pueden colgar el proceso | Aún no |

En los dos casos el riesgo para nosotros es bajo: nuestra configuración de
Caddy no procesa HTML (no usa plantillas) ni lee claves de terceros; lo
confirmo al implementarlo. Pero con la regla de §2 el primero haría fallar
la CI desde el primer día, y no podemos arreglarlo nosotros (decisión 1).

## 4. Decisiones que necesito de ti

1. **Qué hacer con los avisos de Caddy.** Propongo **una excepción
   documentada que caduca en 30 días** en `.trivyignore.yaml`: el motivo
   queda escrito, Dependabot propondrá la versión nueva de Caddy en cuanto
   salga y, si en 30 días no ha salido, la CI vuelve a fallar para que lo
   revisemos. Alternativas: **compilar nuestro propio Caddy** con la librería
   arreglada (arregla hoy, pero tendríamos que mantener esa compilación) o
   **no hacer fallar nunca la CI** con Trivy, solo avisar (más cómodo, pero
   los avisos se acaban ignorando).
2. **Cuándo falla la CI.** Propongo **con avisos altos o críticos que ya
   tienen arreglo**: son los que se pueden y se deben arreglar. Fallar
   también con los que no tienen arreglo bloquearía PR sin que se pueda
   hacer nada; fallar también con los medios llenaría la CI de avisos de
   poco riesgo.
3. **Análisis del propio código (CodeQL).** Propongo **activarlo** también:
   es el analizador gratuito de GitHub, que busca fallos de seguridad en
   **nuestro** código Java y TypeScript (inyecciones, datos sin validar…),
   no en las librerías. Se activa con un botón (*Code scanning → Default
   setup*), sin archivos en el repositorio, y añade una comprobación a cada
   PR que tarda unos minutos. La alternativa es dejarlo fuera: el 7c
   quedaría solo en las dependencias.
