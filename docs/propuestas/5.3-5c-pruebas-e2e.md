# Paso 5c · Pruebas de punta a punta con Playwright (mini propuesta)

> Aprobada el 31/10/2026, con las opciones recomendadas. Fase 5 (Pruebas).
> El 5b está fusionado (PR #16). Un PR: `test/e2e`.

Hasta ahora el backend se prueba sin la web (MockMvc) y la web sin el backend
(MSW). Ninguna prueba comprueba que **las dos partes encajan**: que la web
manda lo que el backend espera, que la cookie del refresh viaja por el proxy,
que el enlace del correo abre la página correcta. El 5c lo cubre con
**Playwright** (decidido en el 5.0): un navegador real contra la web, el
backend y PostgreSQL de verdad. **No cambia el código de la aplicación.**

## 1. Estructura

```
e2e/
├── package.json            ← @playwright/test, aparte de frontend/ (decisión 1 del 5.0)
├── playwright.config.ts    ← arranca el backend y la web antes de las pruebas
├── utilidades/
│   ├── api.ts              ← prepara datos por la API (admin, servicios, empleados, horarios)
│   └── mailpit.ts          ← lee el correo de recuperación en Mailpit
└── pruebas/
    ├── cliente.spec.ts
    ├── menor.spec.ts
    ├── empleado.spec.ts
    ├── horarios.spec.ts
    ├── reserva-admin.spec.ts
    ├── recuperar-password.spec.ts
    └── rgpd.spec.ts
```

- **Cómo arranca:** `playwright.config.ts` levanta el backend (el `.jar`
  compilado, perfil normal) y la web (`npm run build` + `vite preview` en el
  puerto 4173, con el proxy de `/api` que ya existe) y espera a
  `/actuator/health`. PostgreSQL y Mailpit van aparte (decisión 2 del 5.0).
- **Datos:** cada prueba crea lo suyo con nombres y correos únicos (un
  servicio, un empleado, un cliente) por la API, que es rápido, y usa la web
  solo para el flujo que prueba. Así las pruebas no dependen del orden y
  pueden ir en paralelo. El único dato común es el administrador inicial
  (`ADMIN_EMAIL`), que crea el propio backend al arrancar.
- **Fechas:** se reserva dentro de 3 días (más de 24 h, para poder cancelar),
  calculando "hoy" en la zona del negocio. El horario de cada empleado de
  prueba es de lunes a domingo, de 09:00 a 20:00, para que siempre haya horas
  libres sea el día que sea.
- **Selectores:** por rol y texto visible (`getByRole('button', { name:
  'Reservar' })`), como en Testing Library. Así la prueba también comprueba
  que la página se puede usar con un lector de pantalla, y no hace falta
  añadir `data-testid` al código.

## 2. Flujos

| Archivo | Flujo | CU |
|---|---|---|
| `cliente.spec.ts` | Se registra, inicia sesión, ve servicios y profesionales, elige una hora libre en `/horarios`, reserva, la ve en "Mis citas" y la cancela; la hora vuelve a estar libre. Cierra sesión. | CU-001 a 003, 005 a 008, 010 a 012 |
| `menor.spec.ts` | Da de alta a un menor y le reserva una cita; en "Mis citas" sale para quién es. | CU-009 |
| `empleado.spec.ts` | El admin crea un servicio y un empleado en el panel; el empleado entra con la contraseña temporal, la cambia, ve el servicio en "Mis servicios"; un cliente le reserva y el empleado ve la cita en su agenda y la cancela con motivo. | CU-016, 017, 013 a 015, 021, RN-005 |
| `horarios.spec.ts` | El admin pone a un empleado un horario propio y un día de cierre; en `/horarios` cambian las horas libres y el día cerrado ofrece el siguiente con huecos. | CU-018, CU-007, RN-002 |
| `reserva-admin.spec.ts` | El admin busca a un cliente, le reserva una cita desde `/horarios` y la ve en sus reservas con el historial ("por Administrador"). | CU-019 |
| `recuperar-password.spec.ts` | Pide el enlace, lo abre desde el correo de Mailpit, elige otra contraseña e inicia sesión con ella. | CU-020 |
| `rgpd.spec.ts` | Descarga sus datos (comprueba que el JSON no lleva hashes) y elimina su cuenta; ya no puede iniciar sesión. | CU-004, RNF-007 |

El flujo de horarios cambia el horario **de un empleado**, no el general, para
no afectar a las demás pruebas que van en paralelo. "Completada" y "No
presentado" siguen fuera, como acordamos en el 5.0: exigen que la cita ya haya
empezado.

Lo que va en el **5d** (no en este PR): la vista de móvil, la accesibilidad
con axe y la reserva simultánea desde dos navegadores.

## 3. En la CI

Un tercer trabajo, **`e2e`**, que depende de que pasen los de backend y web:

1. Servicios de GitHub Actions: `postgres:16-alpine` y `axllent/mailpit`.
2. Compila el backend (`./mvnw -B -DskipTests package`) y la web.
3. Instala Chromium para Playwright y ejecuta `npx playwright test`.
4. Si algo falla, guarda el **informe de Playwright** como artefacto, con la
   captura de pantalla, el vídeo y la traza de la prueba que falló (se abre
   con `npx playwright show-trace` y deja ver la página paso a paso).

Calculo unos 4 o 5 minutos, en paralelo con nada (va después de los otros dos).

## 4. En tu PC

Una guía nueva, `docs/guias/pruebas-e2e.md`: `docker compose up -d`, crear
una vez la base de datos `gestion_de_citas_e2e` en el mismo contenedor (un
comando), `npm ci` y `npx playwright install chromium` en `e2e/`, y
`npm test`. También `npm run test:ui`, que abre la interfaz de Playwright
para ver las pruebas paso a paso, útil para revisarlas.

## 5. Decisiones que necesito de ti

1. **El límite de 5 inicios de sesión por minuto.** Todas las pruebas inician
   sesión desde la misma IP (`127.0.0.1`), así que lo superarían enseguida.
   Propongo **subirlo solo en las E2E** con una variable de entorno
   (`APP_SECURITY_INTENTOSLOGINPORMINUTO=1000`), que Spring ya lee sin tocar
   el código; el límite ya está probado en el backend (`LimiteIntentosLoginTest`).
   La alternativa es dejarlo en 5 y que las pruebas vayan una a una con pausas,
   lo que las haría mucho más lentas.
2. **Navegadores.** Propongo **solo Chromium** en la CI (Chrome y Edge, la
   mayoría de usuarios). Firefox y WebKit (Safari) triplicarían el tiempo; se
   pueden añadir en la fase 7 si hace falta.
3. **Base de datos en tu PC.** Propongo una base aparte,
   `gestion_de_citas_e2e`, en el mismo contenedor de Docker, para que las
   pruebas no llenen tu base de desarrollo de clientes y servicios de prueba.
4. **Cuándo se ejecutan en la CI.** Propongo **en cada PR y en cada push a
   `main`**, como las demás. La alternativa es solo en `main` o una vez al día,
   que ahorra unos minutos por PR pero avisa tarde.
