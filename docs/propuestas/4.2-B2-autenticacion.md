# Paso 4.2 · B2 · Autenticación (mini propuesta)

> Aprobado el 28/10/2026. Fase 4 (Desarrollo).
> Rama: `feature/autenticacion` → un PR a `main`.

B2 implementa CU-001 (registrarse), CU-002 (iniciar sesión), CU-003 (cerrar
sesión) y CU-004 (perfil y contraseña), con RN-005, RN-006, RNF-001 y RNF-002,
siguiendo el diseño de seguridad del paso 3.4. Además cierra el pendiente del
B1: el aviso `Using generated security password` al arrancar.

## 1. Endpoints

Todos bajo `/api/v1`. Errores siempre en Problem Details.

| Método y ruta | Acceso | Qué hace | Respuestas |
|---|---|---|---|
| `POST /auth/registro` | 🌐 | Crea una cuenta de **cliente** (CU-001). No inicia sesión: la web lleva después al login, como dice la especificación. | 201 con el usuario · 400 formato · 409 correo ya registrado · 422 menor de la edad mínima |
| `POST /auth/login` | 🌐 | Correo + contraseña (CU-002). Devuelve el access token y pone la cookie del refresh token. | 200 · 401 "correo o contraseña no válidos" · 403 cuenta desactivada · 429 demasiados intentos |
| `POST /auth/refresh` | 🌐 con cookie | Nuevo access token y **nuevo** refresh token (rotación). | 200 · 401 cookie ausente, caducada o revocada |
| `POST /auth/logout` | 🌐 con cookie | Revoca el refresh token y borra la cookie (CU-003). | 204 siempre |
| `GET /me` | 🔑 | Mis datos. | 200 |
| `PUT /me` | 🔑 | Cambiar nombre, apellidos, teléfono y correo (CU-004). | 200 · 400 · 409 correo ya usado |
| `PUT /me/password` | 🔑 | Cambiar la contraseña (CU-004) o la temporal del empleado (RN-005). | 200 con tokens nuevos · 400 · 422 contraseña actual incorrecta |

Ejemplo de respuesta de login (y de refresh):

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiraEnSegundos": 900,
  "usuario": { "id": 1, "nombre": "Ana", "rol": "CLIENTE", "debeCambiarPassword": false }
}
```

**Registro**, cuerpo: `nombre`, `apellidos`, `email`, `telefono` (opcional),
`fechaNacimiento`, `password`, `confirmacionPassword`, `aceptaPrivacidad`.
Se guarda `privacidad_aceptada_en` con la hora del `Clock` (RNF-007) y la edad
se calcula con `negocio.edad_minima_cuenta` y la zona del negocio (RN-006).
El 422 del menor dice que un adulto puede reservar por él (RN-007).

## 2. Tokens (paso 3.4)

- **Access token:** JWT firmado con HS256 y la clave `JWT_SECRET` (mínimo 32
  caracteres; si falta o es corta, el backend **no arranca** y dice por qué).
  Dura 15 minutos. Lleva `sub` = id del usuario, `rol` y `dcp` (debe cambiar
  la contraseña). Para emitirlo y validarlo uso el soporte oficial de Spring
  (`spring-boot-starter-oauth2-resource-server`), sin librerías de terceros.
- **Refresh token:** 32 bytes aleatorios (`SecureRandom`), 7 días. En la tabla
  `refresh_token` se guarda su **SHA-256**, no el token. *Cambio pequeño sobre
  el 3.4*: allí ponía "con hash, como las contraseñas", pero BCrypt usa sal y
  no permitiría buscar el token; como el token es aleatorio y larguísimo,
  SHA-256 es igual de seguro aquí y es lo habitual.
- **Rotación:** cada refresh revoca el token usado y crea otro. Si llega un
  token **ya revocado**, se entiende como robo y se revocan todos los tokens
  de ese usuario.
- **Cookie:** `refresh_token`, `HttpOnly`, `Secure`, `SameSite=Strict`,
  7 días. *Cambio pequeño sobre el 3.4*: la ruta de la cookie pasa de
  `/api/v1/auth/refresh` a `/api/v1/auth`, porque el logout también la
  necesita para revocarla.
- **Logout público:** funciona solo con la cookie, así se puede cerrar sesión
  aunque el access token ya haya caducado (CU-003, flujo alternativo 1).
- **Cambiar la contraseña** revoca todas las sesiones abiertas del usuario y
  devuelve tokens nuevos para la sesión actual.

## 3. Contraseñas (RNF-001)

- BCrypt con coste 12.
- Política: de 10 a 64 caracteres (BCrypt solo usa los primeros 72 bytes) y
  no estar en una lista de contraseñas comunes (archivo con unas 200 de las
  más usadas, incluidas en el código).
- Login sin pistas: si el correo no existe se compara igualmente contra un hash
  falso, para que el tiempo de respuesta no revele qué correos están
  registrados.

## 4. Autorización por rol (RNF-002)

| Rutas | Acceso |
|---|---|
| `/api/v1/auth/registro`, `/login`, `/refresh`, `/logout` | Públicas |
| `GET /api/v1/servicios/**`, `/profesionales/**`, `/disponibilidad` | Públicas (los endpoints llegan en B4 y B5; la regla queda ya puesta) |
| `/api/v1/admin/**` | Solo `ADMIN` |
| `/api/v1/empleado/**` | Solo `EMPLEADO` |
| Resto de `/api/v1/**` | Con sesión |
| Swagger y `/actuator/health` | Públicos, como en B1 |

**Contraseña temporal del empleado (RN-005):** el login funciona, pero mientras
el token lleve `dcp = true` solo se permiten `GET /me`, `PUT /me/password`,
`/auth/refresh` y `/auth/logout`; el resto responde **403** "Debes cambiar tu
contraseña antes de continuar". Al cambiarla se pone
`debe_cambiar_password = false` y los tokens nuevos ya llevan `dcp = false`.
(En B2 aún no se crean empleados, eso es B4; la regla se prueba con un
empleado insertado en la prueba.)

**Cuenta desactivada** (`activo = false`): el login responde 403 solo si la
contraseña es correcta (así no se revela nada a quien no la sabe) y el
refresh deja de funcionar.

## 5. Límite de intentos de login (paso 3.4)

5 intentos por minuto **por IP** y **por correo**, con Bucket4j en memoria
(suficiente para un solo servidor). Al pasarse: **429 Too Many Requests** con
la cabecera `Retry-After`. Es un código nuevo en la tabla de errores del 3.2.

## 6. Primer administrador

Un `ApplicationRunner` (`AdministradorInicial`) se ejecuta al arrancar:

- Si `ADMIN_EMAIL` y `ADMIN_PASSWORD` tienen valor y **no existe** ningún
  usuario con ese correo, crea el administrador (nombre `ADMIN_NOMBRE`,
  "Administrador" por defecto) con la contraseña en BCrypt. Lo anota en el log
  sin mostrar la contraseña.
- Si ya existe, no toca nada (cambiar el `.env` después no cambia la
  contraseña; se cambia con `PUT /me/password`).
- Si faltan las variables y no hay ningún administrador, escribe un aviso en
  el log y el backend arranca igual.
- Si `ADMIN_PASSWORD` no cumple la política, el backend no arranca y lo dice.

ya no contiene `Using generated security password`.

## 8. Configuración

`.env.example` gana:

```

ADMIN_EMAIL=admin@ejemplo.com
ADMIN_PASSWORD=cambia-esta-contrasena
ADMIN_NOMBRE=Administrador
COOKIE_SECURE=true        # true también en local: los navegadores aceptan Secure en localhost
```

## 9. Pruebas

- **Unitarias** (JUnit + Mockito): política de contraseñas, cálculo de la
  edad con un `Clock` fijo (cumple 14 justo hoy, le falta un día), emisión y
  lectura del JWT, límite de intentos.
- **Integración** (`@IntegracionTest`, PostgreSQL real):
  - Registro: correcto, correo repetido (409, también con mayúsculas
    distintas), menor de 14 (422), sin aceptar la privacidad (400),
    contraseñas que no coinciden (400).
  - Login: correcto con cookie `HttpOnly`/`SameSite=Strict`, contraseña mal y
    correo inexistente con el **mismo** mensaje (401), cuenta desactivada
    (403), sexto intento en un minuto (429).
  - Refresh: rota el token; reutilizar el viejo revoca todos (401 después);
    logout revoca y el refresh posterior da 401.
  - Roles: un cliente recibe 403 en `/admin/...` y `/empleado/...`; sin token
    401; token caducado o manipulado 401.
  - Empleado con contraseña temporal: 403 en otras rutas, cambia la
    contraseña y ya puede seguir.
  - `/me`: leer, modificar, correo ya usado (409), contraseña actual mal (422).
  - Administrador inicial creado una sola vez, con la contraseña en BCrypt.
  - Arranque sin `Using generated security password`.

## 11. Decisiones que necesito de ti

1. **Los tres cambios pequeños sobre el 3.4**: SHA-256 para el refresh token,
   cookie en `/api/v1/auth` y logout público con cookie.
2. **El registro no inicia sesión** (respeta CU-001 paso 8). La alternativa es
   devolver ya los tokens para ahorrar un paso en la web.
3. **Android** recibirá el refresh token en la misma cookie (las librerías
   HTTP de Android leen cookies). Si prefieres que vaya también en el cuerpo
   para Android, lo dejo para cuando hagamos la app.
