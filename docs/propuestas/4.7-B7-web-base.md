Con el backend terminado (B1 a B6), el B7 abre la web. Crea el proyecto
`frontend/` y todo lo que B8 y B9 van a reutilizar: el cliente de la API con
el token en memoria y la renovación automática, la sesión, las rutas por rol,
el diseño responsive y la CI del frontend. Sobre esa base construye la zona

## 3. Cliente de la API y sesión (paso 3.4)

- **Mismo origen en desarrollo:** Vite reenvía `/api` a `http://localhost:8080`
  (proxy). Para el navegador la web y la API son la misma dirección, así la
  cookie `SameSite=Strict` del refresh token viaja sin problemas y no hace
  falta CORS en local. El CORS del backend se queda para el despliegue (fase 7).
- **Access token solo en memoria** (una variable del módulo `cliente.ts`),
  nunca en `localStorage` ni `sessionStorage`. Se envía como
  `Authorization: Bearer ...`.
- **Al abrir la web** se llama a `POST /auth/refresh`: si la cookie sigue
  viva, el usuario entra sin escribir la contraseña; si no, es visitante.
  Mientras tanto se muestra "Cargando" para no parpadear entre estados.
- **Renovación automática:** si una petición devuelve 401 y había token, se
  pide un refresh y se repite la petición **una sola vez**. Si el refresh
  falla, se borra la sesión y se lleva al login con un aviso ("Tu sesión ha
  caducado") y la página a la que volver.
- **Un solo refresh a la vez.** Es importante por la rotación del B2: si dos
  peticiones (o dos pestañas) renuevan a la vez con la misma cookie, la segunda
  usaría un refresh token ya revocado y el backend **cerraría todas las
  sesiones**. Por eso:
  - dentro de una pestaña, las peticiones que reciben 401 esperan a la misma
    promesa de refresh;
  - entre pestañas, el refresh va dentro de un candado del navegador
    (`navigator.locks`, Web Locks API);
  - el refresh inicial también pasa por ahí, porque en desarrollo el modo
    estricto de React ejecuta los efectos dos veces.
- **Cerrar sesión** (CU-003): `POST /auth/logout`, se borra el token, se vacía
  la caché de TanStack Query y se va al inicio.
- **Errores:** toda respuesta que no sea 2xx se convierte en un `ApiError`
  con `status`, `detail` y la lista `errores` de campo del Problem Details.
  Los formularios ponen cada error de campo debajo de su campo; el resto sale
  en un aviso. Sin conexión: "No se puede conectar con el servidor".
- **TanStack Query:** no reintenta los 4xx (solo errores de red y 5xx, una
  vez); el catálogo se guarda 5 minutos en caché.

- **Cabecera** con el nombre del negocio y el menú (en el móvil, un botón que
  lo despliega); a la derecha "Iniciar sesión" y "Registrarse", o el nombre
  del usuario y "Cerrar sesión".
- **Horas libres en el B7:** se muestran como etiquetas sin acción, con la nota
  "Hora del negocio (Europe/Madrid)". En el B8 cada hora pasa a ser el botón
  que empieza la reserva (si no hay sesión, primero el login y luego vuelve).
- **Fechas:** el selector no deja elegir días pasados ni más allá de
  `antelacionMaxDias` (decisión 1). El backend sigue siendo quien decide (422).
- **`RutaProtegida`** recibe los roles permitidos: sin sesión → login con la
  página de vuelta; con otro rol → "No tienes acceso a esta página". B8 y B9
  solo tienen que añadir sus rutas con el rol.

## 5. Formularios y validación

Zod repite en el navegador las reglas de formato del backend, para avisar
antes de enviar. Las reglas de negocio las sigue decidiendo el servidor.

- **Registro:** nombre (80), apellidos (120), correo, teléfono opcional
  (`+` y de 6 a 19 dígitos o espacios), fecha de nacimiento pasada,
  contraseña de 10 a 64 caracteres escrita dos veces y la casilla "He leído y
  acepto la política de privacidad" con enlace a `/privacidad`. Debajo de la
  fecha: "Debes tener 14 años o más" (con `edadMinimaCuenta`, decisión 1).
  Respuestas: 409 → error en el campo correo; 422 → aviso de la edad mínima;
  400 → errores de cada campo (por ejemplo, contraseña demasiado común, que
  solo sabe el backend).
- **Login:** correo y contraseña obligatorios, nada más (como el backend).
- **Cambiar contraseña:** actual, nueva y confirmación, con las mismas reglas.
- Accesibilidad: cada campo con su `label`, errores enlazados con
  `aria-describedby`, foco en el primer campo con error y botones que se
  desactivan mientras se envía.

## 6. Diseño responsive (RNF-008)

- **Móvil primero**, con puntos de corte en 640 px y 1024 px; las tarjetas
  pasan de una columna a dos y a tres.
- Colores, espacios y tipografía en variables CSS (`estilos/variables.css`):
  un tema sobrio y neutro, fácil de cambiar por otro negocio (versatilidad).
  Modo oscuro según el sistema.
- Fuente del sistema (sin descargas), contraste AA y foco visible con el
  teclado.
- Precios con `Intl.NumberFormat('es-ES', { currency: 'EUR' })` y duraciones
  como "45 min" o "1 h 30 min".

- **CI:** nuevo job `frontend` en `.github/workflows/ci.yml` (Node 24 con

  backend no cambia.

## 9. Pruebas

- **Cliente de la API:** añade el token; con 401 renueva y repite una vez;
  dos peticiones con 401 a la vez hacen **un solo** refresh; si el refresh
  falla, borra la sesión; convierte un Problem Details en `ApiError` con sus
  errores de campo.
- **Sesión:** al arrancar con cookie válida entra con el usuario; sin cookie,
  visitante; `debeCambiarPassword` lleva a `/cambiar-password`;
  `RutaProtegida` (sin sesión → login; rol equivocado → sin acceso).
- **Registro:** validación en el navegador (contraseñas distintas, casilla sin
  marcar), 409 en el campo correo, 422 de edad, éxito → login con el aviso.
- **Login:** correcto (va a la página de origen), 401, 429.
- **Zona pública:** servicios con precio y duración formateados, filtro de
  profesionales, horarios (encadenar los tres pasos, lista de horas, día sin
  horas con el botón a la siguiente fecha, error del servidor).
- **Backend:** la prueba de `GET /negocio` público.

Todas con MSW: no necesitan el backend ni Docker. La prueba de punta a punta
(web + API real) queda para la fase 5, como dice el plan.

## 11. Decisiones que necesito de ti

1. **Nuevo `GET /negocio` público** (§7), un cambio pequeño en el backend
   dentro de un bloque de web. La alternativa es fijar 14 años y 60 días en la
   web, que se desincronizaría si el admin los cambia.
2. **Proxy de Vite en desarrollo** (misma dirección para web y API) en lugar de
   llamar a `localhost:8080` con CORS. Evita líos con la cookie y es como se
   suele desplegar (web y API detrás del mismo dominio). Se decide del todo en
   la fase 7.
3. **Estilos con CSS Modules y variables propias**, sin Tailwind ni librerías
   de componentes (MUI, etc.). Menos dependencias y CSS que entiendes línea a
   línea. La contrapartida: algo más de CSS a mano. Si prefieres Tailwind, lo
   cambio aquí antes de empezar, porque después cuesta más.
4. **Pantalla `/cambiar-password` en el B7** aunque el perfil (CU-004) es del
   B8: sin ella, un empleado con contraseña temporal no podría usar la web
   después de iniciar sesión.
5. **Política de privacidad provisional:** un texto corto y honesto (qué
   datos se guardan, para qué, cómo exportarlos o eliminar la cuenta) que se
   revisará antes del despliegue. Hace falta ya porque el registro pide
   aceptarla.
6. **Recuperar contraseña (CU-020) se queda en el B8**, como dice el plan. Hasta
   entonces, el enlace del correo lleva a una página que la web aún no tiene.
   Si prefieres tenerlo ya, son dos pantallas pequeñas y las meto aquí.
7. **Un solo PR.** Si al terminar queda demasiado grande para revisarlo
   cómodo, lo parto en dos (base + sesión, y zona pública).
