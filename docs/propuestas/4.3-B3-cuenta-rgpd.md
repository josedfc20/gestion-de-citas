# Paso 4.3 · B3 · Cuenta y RGPD (mini propuesta)

> Aprobado el 28/10/2026. Fase 4 (Desarrollo).
> Rama: `feature/recuperar-password-rgpd` → un PR a `main`.

B3 implementa CU-020 (recuperar contraseña), el flujo alternativo 3 de CU-004
(eliminar la cuenta) y el derecho de acceso de RNF-007 (exportar mis datos),
siguiendo los pasos 2.6 (anonimización), 3.3 (endpoints) y 3.4 (límites y RGPD).
La tabla `token_recuperacion` ya existe desde V1.

## 1. Endpoints

Todos bajo `/api/v1`. Errores siempre en Problem Details.

| Método y ruta | Acceso | Qué hace | Respuestas |
|---|---|---|---|
| `POST /auth/recuperar-password` | 🌐 | Cuerpo `{ email }`. Si la cuenta existe y está activa, envía el enlace (CU-020, pasos 1 a 3). | 202 **siempre** con el mismo mensaje · 400 formato · 429 demasiadas solicitudes |
| `POST /auth/restablecer-password` | 🌐 | Cuerpo `{ token, password, confirmacionPassword }`. Guarda la nueva contraseña (pasos 4 a 6). No inicia sesión: la web lleva al login. | 204 · 400 formato, no coinciden o no cumple la política · 422 enlace caducado o ya usado |
| `GET /me/datos` | 🔑 | Exporta mis datos personales en JSON (derecho de acceso). | 200 con `Content-Disposition: attachment; filename="mis-datos.json"` |
| `DELETE /me` | 👤 | Cuerpo `{ password }`. Elimina la cuenta anonimizando los datos (CU-004, alt. 3). | 204 · 403 si no es cliente · 422 contraseña incorrecta |

## 2. Recuperar contraseña (CU-020)

- **Mismo mensaje siempre:** "Si el correo está registrado, recibirás un
  enlace en unos minutos". No se revela qué correos existen.
- **Mismo tiempo siempre:** el correo se envía **en segundo plano** (después
  de confirmar la transacción, con `@Async`), así la respuesta tarda lo mismo
  exista o no la cuenta. Si el envío falla, se anota en el log (sin el token)
  y la respuesta sigue siendo 202.
- **El token:** 32 bytes aleatorios (`SecureRandom`), como el refresh token.
  En `token_recuperacion` se guarda su **SHA-256**, caduca a los **30
  minutos** y es de **un solo uso** (`usado = true`). Al pedir un enlace
  nuevo, los anteriores sin usar del mismo usuario se invalidan: solo vale el
  último.
- **El enlace** apunta a la web (pantalla que llega en B8):
  `{APP_WEB_URL}/restablecer-password#token=...`. Va detrás de `#` para que el
  token no viaje en la petición de la página ni quede en logs o en la cabecera
  `Referer`; la web lo lee y lo manda en el cuerpo del POST.
- **Al restablecer:** BCrypt (coste 12) con la misma política de B2, el token
  queda usado y se **cierran todas las sesiones** del usuario (por si alguien
  tenía la cuenta). Si era un empleado con contraseña temporal, la nueva ya no
  es temporal (`debe_cambiar_password = false`), porque la ha elegido él.
- **Enlace caducado, usado o inventado:** 422 "El enlace no es válido o ha
  caducado. Solicita uno nuevo" (CU-020, alt. 1).
- **Cuentas desactivadas o eliminadas:** no se envía nada (misma respuesta 202).
- **Límite (paso 3.4):** 3 solicitudes por hora **por correo** y 10 por hora
  **por IP**, con Bucket4j como el login. Al pasarse, 429 con `Retry-After`.
  El límite cuenta igual aunque el correo no exista, así tampoco revela nada.

## 3. El correo

- `spring-boot-starter-mail` con un SMTP configurable. En local, **Mailpit**
  en `docker-compose.yml` (SMTP en el puerto 1025 y bandeja web en
  http://localhost:8025): los correos no salen a Internet y se ven en el
  navegador.
- Texto plano en español, con el nombre del negocio de la tabla `negocio`,
  el enlace y el aviso "caduca en 30 minutos; si no lo pediste, ignora este
  correo".
- Una interfaz `EnvioCorreo` en `shared/correo` con la implementación SMTP.
  Las pruebas usan una implementación falsa que guarda los correos en memoria.
  El proveedor SMTP real se elige en la fase 7 (Despliegue).

## 4. Exportar mis datos (`GET /me/datos`)

Disponible para cualquier usuario con sesión (no con contraseña temporal,
como en B2). Ejemplo para un cliente:

```json
{
  "generadoEn": "2026-10-28T15:00:00Z",
  "cuenta": { "id": 7, "rol": "CLIENTE", "nombre": "Ana", "apellidos": "López",
              "email": "ana@correo.com", "telefono": "600000000",
              "creadoEn": "2026-10-20T10:00:00Z" },
  "cliente": { "fechaNacimiento": "1995-04-12",
               "privacidadAceptadaEn": "2026-10-20T10:00:00Z" },
  "sesionesAbiertas": [ { "iniciadaEn": "2026-10-28T09:00:00Z", "expiraEn": "2026-11-04T09:00:00Z" } ],
  "beneficiarios": [],
  "citas": []
}
```

Nunca incluye el hash de la contraseña ni los hashes de los tokens.
`beneficiarios` y `citas` salen vacíos hasta el **B6**, que los rellenará
(queda anotado en `AGENTS.md` para no olvidarlo).

## 5. Eliminar la cuenta (`DELETE /me`)

- **Solo clientes** (como en el 3.3). Los empleados los desactiva el
  administrador (B4) y el administrador no puede borrarse a sí mismo para no
  dejar el negocio sin administrador.
- **Confirmación con la contraseña** en el cuerpo: si alguien encuentra la
  sesión abierta, no puede borrar la cuenta.
- **Anonimización (paso 2.6):** no se borra la fila, porque las citas son
  historial del negocio. En una sola transacción:

| Dato | Queda así |
|---|---|
| `nombre` / `apellidos` | "Usuario" / "eliminado" |
| `email` | `eliminado-{id}@anonimo.invalid` (único y el dominio `.invalid` nunca recibe correo) |
| `telefono` | vacío |
| `password_hash` | hash de un valor aleatorio que nadie conoce |
| `activo` | `false` |
| `eliminado_en` (nuevo) | hora del `Clock` |
| `cliente.fecha_nacimiento` | vacío |
| `cliente.privacidad_aceptada_en` | se conserva (prueba de que hubo consentimiento) |
| `refresh_token` y `token_recuperacion` | se borran las filas |

- La cookie del refresh token se borra en la respuesta. El access token que
  tenga la web sigue siendo válido como mucho 15 minutos, pero ya solo ve
  datos anónimos y cualquier renovación da 401.
- **B6 completará** la eliminación: anonimizar los beneficiarios (datos de
  menores) y cancelar las citas futuras confirmadas con el motivo "Cuenta
  eliminada" para liberar los huecos. Hoy esas tablas siguen vacías.

## 6. Base de datos: migración V4

```sql
ALTER TABLE usuario ADD COLUMN eliminado_en TIMESTAMPTZ;      -- distingue "eliminada" de "desactivada"
ALTER TABLE cliente ALTER COLUMN fecha_nacimiento DROP NOT NULL; -- se vacía al anonimizar
CREATE INDEX ix_token_recuperacion_usuario ON token_recuperacion (usuario_id);
```

`eliminado_en` sirve para que una cuenta eliminada no se pueda reactivar
nunca (en B4 el administrador podrá reactivar empleados desactivados, pero no
cuentas eliminadas). V1 a V3 no se tocan.

## 9. Pruebas

- **Unitarias:** límite de solicitudes (cuarta en una hora por correo, 429),
  caducidad del token con un `Clock` fijo (29 y 31 minutos), texto del correo
  con el enlace correcto.
- **Integración** (`@IntegracionTest`, PostgreSQL real, correo falso):
  - Recuperar: correo existente (se envía un correo con enlace), inexistente
    y desactivado (misma respuesta 202 y ningún correo), cuarta solicitud
    (429), segunda solicitud invalida el primer enlace.
  - Restablecer: correcto (login con la nueva funciona y con la vieja no;
    sesiones anteriores cerradas), mismo enlace dos veces (422), caducado
    (422), token inventado (422), contraseñas que no coinciden o comunes (400),
    empleado con contraseña temporal queda con `debe_cambiar_password = false`.
  - Exportar: contiene los datos esperados y **no** contiene el hash de la
    contraseña; sin sesión 401; empleado con contraseña temporal 403.
  - Eliminar: contraseña mal (422), empleado o admin (403), correcto (datos
    anonimizados en la BD, login imposible, refresh 401, el correo original
    puede registrarse de nuevo, recuperar contraseña con el correo original no
    envía nada).

## 11. Decisiones que necesito de ti

1. **Anonimizar con la migración V4** (`eliminado_en` y fecha de nacimiento
   que admite vacío). La alternativa sin tocar el esquema es poner una fecha
   ficticia (1900-01-01), pero mezcla datos falsos con reales.
2. **Solo los clientes pueden eliminar su cuenta** desde la app; empleados y
   administrador no (lo dice el 3.3, lo confirmo).
3. **Al eliminar la cuenta, B6 cancelará las citas futuras** automáticamente.
   La alternativa es impedir la eliminación (409) mientras tenga citas futuras
   y pedirle que las cancele antes.
4. **`DELETE /me` con la contraseña en el cuerpo.** Funciona en navegadores y
   Android; si prefieres evitar un `DELETE` con cuerpo, sería
   `POST /me/eliminacion`.
