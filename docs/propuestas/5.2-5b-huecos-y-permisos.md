# Paso 5b · Huecos, matriz de permisos y umbral de cobertura (mini propuesta)

> Aprobada el 31/10/2026, con las opciones recomendadas. Fase 5 (Pruebas).
> El 5a está fusionado (PR #15). Un PR: `test/huecos-permisos`.

El 5a midió la cobertura y dejó en `docs/pruebas/matriz-trazabilidad.md` diez
huecos (H-1 a H-10). El 5b cubre los que se prueban sin la aplicación entera
(los de móvil, accesibilidad y dos navegadores van en el 5c y el 5d) y fija un
mínimo de cobertura que hace fallar la CI. **No cambia el comportamiento de la
aplicación**; el único cambio en el código es quitar un método que nadie usa
(decisión 3).

## 1. Matriz de permisos del backend (H-5, RNF-002)

Hoy cada clase de pruebas comprueba los permisos de sus endpoints ("solo el
admin…", "solo los empleados…"). Funciona, pero nada avisa si mañana se añade un
endpoint y se olvida protegerlo. Propongo una prueba nueva, **`PermisosTest`**:

- **Una tabla con los 54 endpoints** de la API y quién puede usar cada uno:
  público, cualquier usuario con sesión, cliente, empleado o admin, sacada de
  `SecurityConfig` y del paso 3.3.
- **Cinco perfiles:** anónimo, cliente, empleado, **empleado con la contraseña
  temporal** (RN-005: solo puede usar `GET /me` y `PUT /me/password`) y admin.
- Para cada endpoint y perfil (270 casos, en una prueba parametrizada):
  - quien no tiene sesión y no debe entrar → **401**;
  - quien tiene sesión y no debe entrar → **403**;
  - quien sí puede entrar → cualquier respuesta **que no sea 401 ni 403**.
    No se comprueba que la petición salga bien (puede dar 400 por un cuerpo
    vacío o 404 por un id inventado), solo que la seguridad la deja pasar.
- **Prueba de que la tabla está completa:** lee de Spring todos los endpoints
  que existen de verdad y falla si alguno no está en la tabla (o si la tabla
  tiene uno que ya no existe). Así, un endpoint nuevo obliga a decidir quién
  puede usarlo.

Lo de "lo ajeno da 404" (un cliente que pide la cita de otro) ya está probado
en cada clase (`cadaUnoVeElDetalleDeLoSuyo`, `unBeneficiarioAjenoNoExiste`,
`elEmpleadoSoloCambiaSusCitas…`) y no lo repito.

**En la web**, lo mismo con las rutas: una prueba recorre todas las rutas
privadas de `rutas.tsx` con los cuatro perfiles y comprueba que cada uno ve la
página o es enviado al login o a su página de inicio. Hoy solo se prueban
algunas rutas sueltas.

## 2. Reglas de arquitectura con ArchUnit (H-7, RNF-006)

ArchUnit comprueba la estructura del código con pruebas JUnit normales, sin
cambiar nada del código. Reglas del paso 3.2 que hoy nadie vigila:

| Regla | Origen |
|---|---|
| Un controller nunca usa un repository | 3.2: Controller → Service → Repository |
| Los controllers no devuelven entidades (`@Entity`), solo DTO | 3.2: "la API usa DTOs" |
| `usuario` y `beneficiario` no dependen de `cita` | B6: interfaces `AportaDatosPersonales` y `CitasDeBeneficiario` |
| Nadie llama a `LocalDate.now()`, `LocalDateTime.now()`, `Instant.now()`, etc. sin un `Clock` | 3.2: "usar un `Clock` inyectado" |
| `CalculoDisponibilidad` no depende de Spring | B5 |

Si alguna regla falla con el código actual, **no lo arreglo en este PR**: te lo
enseño y decidimos (sería un defecto para el 5e).

## 3. Huecos funcionales

**Backend** (los he sacado de las líneas que JaCoCo marca sin ejecutar; solo
las que son reglas de negocio, no las defensivas):

| Prueba nueva | Qué no se probaba |
|---|---|
| Editar un empleado poniendo el correo de otra cuenta → 409 | `EmpleadoService`, solo se probaba en el alta |
| Editar un servicio poniendo el nombre de otro → 409 | `ServicioService`, solo se probaba en el alta |
| `GET /admin/servicios/{id}` devuelve el servicio | **Ningún test llamaba a este endpoint**, y la web lo usa en la ficha del servicio |
| Los avisos y el 409 cuentan las citas en singular y en plural ("1 cita futura", "2 citas futuras") | Solo se probaba un caso de cada mensaje |
| Restablecer la contraseña con un enlace válido de una cuenta desactivada después de pedirlo → 422 | `RecuperacionPasswordService` |
| Pedir la disponibilidad del último día permitido sin huecos no sugiere otro día | `DisponibilidadService` |
| Guardar el perfil con el teléfono en blanco lo deja vacío | `PerfilService` |
| Cancelar con un motivo de solo espacios lo guarda vacío | `Cita` |

**Correo con Mockito (H-9):** `EnvioCorreoSmtp` (hoy 41,7 %) con un
`JavaMailSender` simulado, para comprobar remitente, destinatario, asunto y
texto; y que si el envío falla, `POST /auth/recuperar-password` responde igual
(202) y el error queda en el log sin el token. Es el uso de Mockito que
acordamos en el 5.0 ("solo donde una prueba de integración no llegue").

**Web:**

| Hueco | Prueba nueva |
|---|---|
| H-1 | Volver a activar un servicio desactivado |
| H-2 | Volver a activar un empleado y editar sus datos personales |
| H-3 | "Ver también los de los últimos 90 días" en los días de cierre (quitar un cierre del negocio ya estaba probado) |
| H-4 | El admin cancela una reserva con motivo desde su detalle y el historial se actualiza |

**Lo que no propongo probar:** las líneas defensivas que solo se ejecutan si la
base de datos está rota ("No existe el registro del negocio (migración V2)"),
si falta un archivo del propio `.jar` o si Java no tiene SHA-256, y los
`catch` de las carreras entre dos peticiones iguales que ya cubre la
restricción de la base de datos. Tampoco renovar la sesión de una cuenta
desactivada: desactivar ya borra sus sesiones y eso sí está probado. Probarlas
sube la cifra pero no demuestra nada.

## 4. Umbral de cobertura

Con lo que hay hoy (backend 97,2 % de líneas y 84,8 % de ramas; web 91,3 % y
80,3 %), el 80 % que propuse en el 5.0 no detectaría nada. Propongo:

| Parte | Líneas | Ramas | Herramienta |
|---|---|---|---|
| Backend | **95 %** | **85 %** | `jacoco:check` en `mvn verify` |
| Web | **90 %** | **80 %** | `coverage.thresholds` de Vitest en `npm run test:cobertura` |

Están un poco por debajo de lo que habrá tras este PR, para que una pequeña
refactorización no rompa la CI, pero lo bastante altos para que un bloque nuevo
sin pruebas sí la rompa. Se revisan al cerrar la fase.

## 5. Decisiones que necesito de ti

1. **Umbral:** 95/85 en el backend y 90/80 en la web (recomendado), o
   quedarnos con el 80 % del plan 5.0.
2. **ArchUnit:** añadirlo (recomendado; es una dependencia solo de pruebas) o
   dejar las reglas de arquitectura sin prueba automática.
3. **Código muerto:** `EstadoCita.ocupa()` no lo usa nadie (la restricción de
   la base de datos hace ese trabajo). Propongo **borrarlo** en lugar de
   escribirle una prueba. La alternativa es dejarlo y probarlo.
