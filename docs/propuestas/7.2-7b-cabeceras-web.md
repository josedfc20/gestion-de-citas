# Paso 7b · HTTPS y cabeceras de seguridad de la web (mini propuesta)

> Aprobada el 14/11/2026, con las opciones recomendadas (pruebas de
> producción en cada PR y sin receptor de avisos de la CSP). Fase 7 (Despliegue).
> El 7a se fusionó con el PR #27.

El 7a ya da HTTPS: Caddy pide el certificado y pasa de HTTP a HTTPS. Lo que
falta es lo que **el navegador debe hacer con la web**: no volver nunca a
HTTP, no ejecutar código que no sea nuestro y no dejar que otra página la
meta en un marco. Eso se le dice con cabeceras. El backend ya manda las suyas
en la API (`seguridad.spec.ts`, 5d); la web, servida por Caddy, todavía no
manda ninguna. Este paso las añade y las prueba **automáticamente contra el
Compose de producción**, porque ninguna prueba actual pasa por Caddy.

## 1. Las cabeceras (en el `Caddyfile`)

| Cabecera | Valor | Para qué |
|---|---|---|
| `Strict-Transport-Security` | `max-age=31536000` (1 año) | El navegador ya no intenta HTTP con esta dirección durante un año, ni aunque alguien escriba `http://` (RNF-004). Sin `preload`: con un subdominio de DuckDNS no se puede pedir y es muy difícil de deshacer |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` | Solo se ejecuta y se carga lo que viene de nuestra dirección. Si un día alguien consiguiera colar un `<script>` en un dato (XSS), el navegador no lo ejecutaría. Lo he comprobado en la web compilada: no tiene scripts ni estilos en línea ni carga nada de fuera, así que **no hace falta `unsafe-inline`** |
| `X-Content-Type-Options` | `nosniff` | El navegador no "adivina" el tipo de un archivo |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Al salir a otra web solo se manda el dominio, nunca la ruta (que puede llevar el id de una cita) |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` | La web no usa nada de eso; si algo lo intenta, el navegador lo bloquea |
| `Cross-Origin-Opener-Policy` | `same-origin` | Otra pestaña abierta desde fuera no puede tocar la nuestra |
| `Server` | se quita | No anunciar qué servidor hay |

Y la **caché**: `/assets/*` (los archivos con huella en el nombre, como
`index-BY1HMJhv.js`) con `max-age` de un año e `immutable`; `index.html`
y las rutas de React con `no-cache`, para que una versión nueva se vea al
momento. Las respuestas de `/api` conservan las cabeceras del backend
(`Cache-Control: no-store`, `X-Frame-Options: DENY`).

## 2. Las pruebas: `e2e/produccion/`

Una configuración de Playwright aparte, `playwright.produccion.config.ts`
(como la de las capturas del 6c): no arranca backend ni web, sino que prueba
la dirección que se le dé, por defecto `https://localhost` con el Compose de
producción. En el 7f será la dirección pública.

| Prueba | Qué comprueba |
|---|---|
| `cabeceras.spec.ts` | Las cabeceras de §1 en `/`, en una ruta de React y en `/api/v1/negocio`; la caché de `/assets/*` y de `index.html`; que no hay cabecera `Server` |
| `https.spec.ts` | `http://` responde 308 hacia `https://` con la misma ruta; Swagger y `/actuator` no se ven desde fuera |
| `csp.spec.ts` | Recorre las páginas de los cuatro perfiles (visitante, cliente, empleado y admin de la demo) y falla si el navegador registra **una sola infracción de la CSP**. Así, si mañana alguien añade un `style={{...}}` o un script de fuera, la CI lo para antes de llegar a producción |
| `sesion.spec.ts` | Por HTTPS y a través de Caddy: login, la sesión sigue al recargar (la cookie `Secure` viaja), reservar y cerrar sesión |

**En la CI**, un trabajo nuevo **"Producción"** (después de las pruebas,
en paralelo con las imágenes): construye las imágenes (aprovechando la caché
del trabajo "Imágenes"), arranca `docker-compose.prod.yml` con el perfil
`demo` y `DOMINIO=localhost`, y pasa `e2e/produccion/`. Si falla, guarda el
informe de Playwright y los logs de los tres contenedores.

En el PC: `cd e2e && npm run produccion` con el Compose de producción
arrancado (la guía `desplegar.md` lo explica).

## 4. Decisiones que necesito de ti

1. **Cuándo corren las pruebas de producción en la CI.** Propongo **en cada
   PR**: añaden unos 4 o 5 minutos, pero una CSP se rompe sobre todo desde la
   web (un estilo en línea, una librería nueva que inyecta algo), y eso solo
   se ve pasando por Caddy. La alternativa es **solo cuando cambian los
   archivos de producción** (`Caddyfile`, `Dockerfile`, Compose): más rápido,
   pero un cambio en la web que rompa la CSP llegaría a `main` sin aviso.
2. **Avisos de la CSP en producción.** Propongo **no montar un receptor de
   avisos** (`report-to`): las pruebas ya recorren todas las páginas y sería
   otro endpoint público que mantener. La alternativa es un endpoint pequeño
   en el backend que apunte en el log cada infracción que vea un usuario
   real: útil en una aplicación grande, poco para una demo.
