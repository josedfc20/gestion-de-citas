> Guía para leer `diagramas/ER-BaseDeDatos.png` junto con
> `propuestas/2.6-esquema-borrador.sql`. Primero la notación, luego cada tabla
> columna a columna, después cómo se relacionan, un ejemplo con datos reales,

---

## 1. Diagrama de clases vs. diagrama entidad-relación (ER)

| Diagrama de clases (paso 2.4) | Diagrama ER (paso 2.6) |
|---|---|
| Piensa en **objetos** de Java | Piensa en **tablas** de PostgreSQL |
| Herencia directa (`Cliente` es un `Usuario`) | Las bases de datos relacionales no tienen herencia: se simula con tablas y claves |
| Relación muchos a muchos con una sola línea | Necesita una **tabla intermedia** |
| Tipos de Java (`String`, `BigDecimal`) | Tipos de SQL (`varchar`, `numeric`) |

El ER es el "plano" exacto de cómo se guardarán los datos en disco.

## 2. Cómo se lee cada tabla

```
┌──────────────────────────────────────┐
│               cita                   │ ← nombre de la tabla
├──────────┬──────────────┬────┬───────┤
│ bigint   │ id           │ PK │       │ ← tipo | columna | clave | comentario
│ bigint   │ cliente_id   │ FK │       │
│ bigint   │ beneficiario_id │ FK │ NULL = para el cliente │
└──────────┴──────────────┴────┴───────┘
```

- **PK (Primary Key, clave primaria):** identifica cada fila de forma única. Nunca se repite ni puede estar vacía. Aquí casi siempre es `id`, un número que PostgreSQL genera solo (1, 2, 3…).
- **FK (Foreign Key, clave foránea):** una columna que **apunta** a la PK de otra tabla. `cita.cliente_id = 7` significa "esta cita es del cliente con id 7". La base de datos no deja guardar un 7 si no existe ese cliente (**integridad referencial**).
- **UK (Unique Key, clave única):** no puede repetirse, pero no es la PK. Por ejemplo, `usuario.email`.
- **PK, FK a la vez:** la columna identifica la fila *y* apunta a otra tabla (lo vemos en la herencia).

### Tipos de datos usados

| Tipo SQL | Qué guarda | Equivalente Java |
|---|---|---|
| `bigint` | Entero grande (ids) | `Long` |
| `int`, `smallint` | Entero / entero pequeño | `int` / `short` |
| `varchar(n)` | Texto de hasta *n* caracteres | `String` |
| `text` | Texto sin límite práctico | `String` |
| `boolean` | Verdadero/falso | `boolean` |
| `numeric(10,2)` | Número exacto con 2 decimales (dinero) | `BigDecimal` |
| `date` | Solo fecha | `LocalDate` |
| `time` | Solo hora | `LocalTime` |
| `timestamptz` | Fecha y hora con zona horaria | `OffsetDateTime` / `Instant` |

## 3. Cómo se leen las líneas: notación "pata de gallo" (crow's foot)

Cada extremo de una línea tiene un símbolo que indica **cuántas filas** de esa
tabla participan:

| Símbolo en el extremo | Significa | Equivale a |
|---|---|---|
| `││` (dos rayas) | exactamente uno | `1` |
| `○│` (círculo y raya) | cero o uno | `0..1` |
| `○<` (círculo y pata de gallo) | cero o muchos | `0..*` |
| `│<` (raya y pata de gallo) | uno o muchos | `1..*` |

La **raya** significa "obligatorio", el **círculo** "opcional" y la **pata de
gallo** "muchos".

**Ejemplo:** `cliente ││──○< cita` se lee:
- "Cada cita pertenece a **exactamente un** cliente" (las dos rayas junto a *cliente*).
- "Un cliente tiene **cero o muchas** citas" (círculo y pata junto a *cita*).

Y en la tabla eso se traduce en que `cita` tiene la columna `cliente_id`
(FK, obligatoria). **Regla de oro:** la FK siempre va en la tabla del lado
"muchos".

## 4. Las tablas, una a una

### 4.1 `negocio` — la configuración
| Columna | Para qué |
|---|---|
| `id` | Identificador (habrá una sola fila en el MVP). |
| `nombre` | Nombre del establecimiento. |
| `zona_horaria` | Por defecto `Europe/Madrid`. Sirve para que "10:00" sea siempre la hora local, también con el cambio de hora de verano. |
| `intervalo_minutos` | 30 (RN-010). |
| `antelacion_max_dias` | 60 (RN-009). |
| `horas_min_cancelacion` | 24 (RN-004). |
| `edad_minima_cuenta` | 14 (RN-006). |

Todas tienen un `CHECK` que impide valores absurdos (por ejemplo, un intervalo de 0 minutos).

### 4.2 `usuario`, `cliente` y `empleado` — la herencia
Las bases de datos relacionales **no tienen herencia**. La simulamos así
(estrategia *joined*, "tabla por subclase"):

```
usuario (id=1, rol=CLIENTE, nombre=Ana, ...)      ← datos comunes
   └── cliente (usuario_id=1, fecha_nacimiento=...) ← datos propios del cliente
usuario (id=2, rol=EMPLEADO, nombre=Luis, ...)
   └── empleado (usuario_id=2, debe_cambiar_password=false)
usuario (id=3, rol=ADMIN, nombre=Marta, ...)      ← el admin no necesita más
```

- `cliente.usuario_id` es **PK y FK a la vez**: el cliente 1 *es* el usuario 1. Por eso la línea `usuario ││──○│ cliente` es "uno a cero-o-uno": un usuario puede tener (o no) su fila de cliente.
- `rol` dice qué tipo de usuario es y está limitado por `CHECK` a `CLIENTE`, `EMPLEADO` o `ADMIN`.
- `email` es único **sin distinguir mayúsculas** gracias al índice sobre `lower(email)`.
- `password_hash`: nunca la contraseña (RNF-001).
- `activo`: desactivar en lugar de borrar.
- `creado_en`: cuándo se creó la cuenta.

### 4.3 `token_recuperacion`
| Columna | Para qué |
|---|---|
| `usuario_id` (FK) | De quién es el enlace. |
| `token_hash` (UK) | El código del enlace, guardado con hash como las contraseñas: si alguien robara la base de datos no podría usar los enlaces. |
| `expira_en` | Ahora + 30 minutos (CU-020). |
| `usado` | Un solo uso. |

### 4.4 `beneficiario`
El menor. `cliente_id` (FK) apunta a su adulto responsable. Solo nombre,
apellidos y fecha de nacimiento (minimización RGPD).

### 4.5 `servicio`
`nombre` único, `duracion_minutos` > 0, `precio` `numeric(10,2)` ≥ 0, `activo`.

### 4.6 `empleado_servicio` — la tabla intermedia
Resuelve el **muchos a muchos** "un empleado realiza varios servicios y un
servicio lo realizan varios empleados". Cada fila es una pareja:

| empleado_id | servicio_id |
|---|---|
| 2 (Luis) | 1 (Corte) |
| 2 (Luis) | 2 (Corte infantil) |
| 4 (Sara) | 1 (Corte) |

Su PK es **compuesta** `(empleado_id, servicio_id)`: así no puede repetirse la misma pareja.

### 4.7 `tramo_horario` y `dia_cierre`
- `negocio_id` (FK, obligatoria) y `empleado_id` (FK, **opcional**):
  - `empleado_id` vacío → horario general / cierre de todo el negocio.
  - `empleado_id` relleno → ajuste o vacaciones de ese empleado.
- `dia_semana`: 1 = lunes … 7 = domingo (estándar ISO).
- `CHECK (hora_inicio < hora_fin)`: impide tramos al revés.

### 4.8 `cita` — la tabla central
| Columna | Para qué |
|---|---|
| `cliente_id` (FK) | Quién reserva (siempre un adulto con cuenta). |
| `empleado_id` (FK) | Quién atiende. |
| `servicio_id` (FK) | Qué se hace. |
| `beneficiario_id` (FK, opcional) | Para quién, si es un menor. Vacío = para el propio cliente. |
| `inicio`, `fin` | Cuándo. El fin se guarda (no se calcula) para que no cambie si cambia la duración del servicio. |
| `precio` | Copia del precio al reservar. |
| `estado` | Uno de los 4 de RN-008 (`CHECK`). Por defecto `CONFIRMADA`. |
| `motivo_cancelacion` | Solo si se cancela. |
| `creada_en` | Cuándo se reservó. |

Y tres protecciones:
1. `CHECK (inicio < fin)`.
2. **`no_solape_profesional`** (ver sección 7).
3. Índices para que las búsquedas frecuentes sean rápidas (sección 8).

### 4.9 `cambio_estado_cita` — el historial
`cita_id` (FK), `estado_anterior` (vacío al crear), `estado_nuevo`, `fecha` y
`realizado_por` (FK a `usuario`: puede ser cliente, empleado o admin).

`ON DELETE CASCADE` refleja la **composición** del diagrama de clases: si algún
día se borrara una cita, su historial se borraría con ella.

## 5. Las relaciones del diagrama, leídas

| Línea | Lectura | Dónde está la FK |
|---|---|---|
| negocio ││──○< tramo_horario | Un negocio tiene 0..* tramos; cada tramo es de un negocio | `tramo_horario.negocio_id` |
| negocio ││──○< dia_cierre | Igual con los cierres | `dia_cierre.negocio_id` |
| usuario ││──○│ cliente / empleado | Un usuario es, como mucho, un cliente (o un empleado) | `cliente.usuario_id`, `empleado.usuario_id` |
| usuario ││──○< token_recuperacion | Un usuario puede pedir varios enlaces | `token_recuperacion.usuario_id` |
| cliente ││──○< beneficiario | Un cliente es responsable de 0..* menores | `beneficiario.cliente_id` |
| cliente ││──○< cita | Un cliente reserva 0..* citas | `cita.cliente_id` |
| empleado ││──○< cita | Un empleado atiende 0..* citas | `cita.empleado_id` |
| servicio ││──○< cita | Un servicio aparece en 0..* citas | `cita.servicio_id` |
| beneficiario ○│──○< cita | Una cita tiene 0 o 1 beneficiario | `cita.beneficiario_id` (opcional) |
| empleado ││──○< empleado_servicio ○>──││ servicio | Muchos a muchos a través de la tabla intermedia | Las dos columnas de `empleado_servicio` |
| empleado ○│──○< tramo_horario / dia_cierre | Un tramo o cierre puede ser de un empleado | `empleado_id` (opcional) |
| cita ││──○< cambio_estado_cita | Una cita tiene 0..* cambios | `cambio_estado_cita.cita_id` |
| usuario ││──○< cambio_estado_cita | Cada cambio lo hizo un usuario | `cambio_estado_cita.realizado_por` |

## 6. Ejemplo con datos reales

> Ana reserva un **Corte infantil** con **Luis** el martes 3 de noviembre a las
> 10:00 para su hija **Lucía**.

**usuario**
| id | rol | nombre | email |
|---|---|---|---|
| 1 | CLIENTE | Ana | ana@correo.com |
| 2 | EMPLEADO | Luis | luis@negocio.com |
| 3 | ADMIN | Marta | marta@negocio.com |

**cliente** → `(usuario_id=1, fecha_nacimiento=1990-05-12, privacidad_aceptada_en=2026-10-20 18:03)`
**empleado** → `(usuario_id=2, debe_cambiar_password=false)`
**beneficiario** → `(id=1, cliente_id=1, nombre=Lucía, fecha_nacimiento=2017-03-08)`
**servicio** → `(id=2, nombre=Corte infantil, duracion_minutos=30, precio=12.00)`
**empleado_servicio** → `(empleado_id=2, servicio_id=2)`

**cita**
| id | cliente_id | empleado_id | servicio_id | beneficiario_id | inicio | fin | precio | estado |
|---|---|---|---|---|---|---|---|---|
| 1 | 1 | 2 | 2 | 1 | 2026-11-03 10:00 | 2026-11-03 10:30 | 12.00 | CONFIRMADA |

**cambio_estado_cita**
| id | cita_id | estado_anterior | estado_nuevo | realizado_por |
|---|---|---|---|---|
| 1 | 1 | *(vacío)* | CONFIRMADA | 1 (Ana) |
| 2 | 1 | CONFIRMADA | COMPLETADA | 2 (Luis) |

Fíjate: la cita no guarda "Ana", "Luis" ni "Corte infantil" como texto, solo
**números que apuntan** a esas filas. Si Ana cambia su teléfono, se cambia en
un único sitio.

## 7. La protección contra solapes, en detalle (RNF-003)

```sql
CONSTRAINT no_solape_profesional EXCLUDE USING gist (
    empleado_id WITH =,
    tstzrange(inicio, fin, '[)') WITH &&
) WHERE (estado IN ('CONFIRMADA','COMPLETADA'))
```

Se lee: *"No puede haber dos filas con el **mismo** `empleado_id` (`=`) cuyos
intervalos de tiempo se **solapen** (`&&`), considerando solo las citas
Confirmadas o Completadas."*

- `tstzrange(inicio, fin, '[)')` crea un intervalo que **incluye** el inicio y
  **excluye** el fin. Por eso 10:00–10:30 y 10:30–11:00 no chocan.
- `WHERE (...)`: las canceladas y los "no presentado" no ocupan hueco.
- `gist` es el tipo de índice que sabe comparar intervalos; `btree_gist` le
  permite comparar también el `empleado_id`.

**¿Por qué en la base de datos y no solo en Java?** Si dos peticiones llegan a
la vez, las dos podrían comprobar "está libre" antes de que ninguna guarde
(*condición de carrera*). La base de datos procesa los guardados de uno en uno
contra esta regla, así que **una** entra y la otra recibe un error, que Java
convierte en "Esa hora ya no está disponible".

**Lo probé en PostgreSQL 16:**
| Prueba | Resultado |
|---|---|
| Luis 10:00–10:30 y luego 10:30–11:00 | Las dos se guardan ✔ |
| Luis 10:15–10:45 con las anteriores activas | Rechazada: `violates exclusion constraint "no_solape_profesional"` ✔ |
| Cancelar la de 10:00 y volver a reservar 10:00 | Se guarda ✔ |
| Registrar `A@X.com` existiendo `a@x.com` | Rechazado por `ux_usuario_email` ✔ |

## 8. Consultas importantes y los índices que las aceleran

**"Mis citas" (CU-010)**
```sql
SELECT c.inicio, s.nombre AS servicio, u.nombre AS profesional, c.estado
FROM cita c
JOIN servicio s ON s.id = c.servicio_id
JOIN usuario  u ON u.id = c.empleado_id
WHERE c.cliente_id = :cliente AND c.inicio >= now()
ORDER BY c.inicio;
```
→ usa el índice `ix_cita_cliente_inicio (cliente_id, inicio)`.

**Citas que ocupan a un profesional un día (CU-007)**
```sql
SELECT inicio, fin FROM cita
WHERE empleado_id = :empleado
  AND estado IN ('CONFIRMADA','COMPLETADA')
  AND inicio < :finDelDia AND fin > :inicioDelDia;
```
→ usa `ix_cita_empleado_inicio (empleado_id, inicio)`.

**Horario que aplica a un empleado un lunes (RN-002)**
```sql
SELECT hora_inicio, hora_fin FROM tramo_horario
WHERE dia_semana = 1 AND empleado_id = :empleado;
-- si no devuelve filas, se usa el horario general:
SELECT hora_inicio, hora_fin FROM tramo_horario
WHERE dia_semana = 1 AND empleado_id IS NULL;
```

`JOIN` une tablas a través de sus claves: así se "reconstruye" la información
que repartimos entre tablas.

Un **índice** es como el índice de un libro: sin él, PostgreSQL leería todas
las citas para encontrar las de un cliente; con él, va directo.

## 9. Normalización: por qué está repartido así

La normalización son reglas para evitar datos duplicados e incoherentes:

| Forma normal | Regla | Cómo la cumplimos |
|---|---|---|
| **1FN** | Cada celda guarda un solo valor | Los servicios de un empleado no van en una columna "1,2,5", sino en filas de `empleado_servicio` |
| **2FN** | Todo depende de la clave completa | En `empleado_servicio` no hay columnas que dependan solo de una de las dos claves |
| **3FN** | Nada depende de otra columna que no sea la clave | El nombre del cliente está en `usuario`, no copiado en cada cita |

### La excepción deliberada: `cita.precio` y `cita.fin`
Copiarlos parece romper la 3FN (ya están en `servicio`), pero **no son el mismo
dato**: `servicio.precio` es el precio *actual*; `cita.precio` es el precio
*que se pactó ese día*. Guardarlo es correcto y habitual (igual que una factura
guarda el precio de cada línea).
